## 3. 문서 건수 세는 법 (가이드)

- Studio에서는 케이스 1건 = 실행 1번 = 결과 1건이다.
- 케이스를 만드는 방법은 세 가지 모두 된다.
  - 문서 1건을 그대로 올림 → 문서 1건 = 케이스 1건
  - 서류 여러 종을 PDF 1개로 합침 → 파일 1개 = 케이스 1건
  - 파일 여러 개를 업로드 메뉴의 **통합 업로드**로 함께 올림 → 파일 여러 개 = 케이스 1건
- 문서 건수는 케이스 안의 **문서 종류별로 1건씩** 센다. PDF 1개에 서류 4종이면 4건이다.
- 미션 2는 10건, 최종 제출은 **20건 이상**이다. 20건 미만이면 제출 조건을 충족하지 못한 것으로 본다. (피드백)

## 4. 산출물별 작성 규칙

### 4.1 설계서 (가이드, 피드백)

- 1장 분량, PDF로 제출한다. 템플릿의 회색 안내 · 예시 문구는 지운다.
- 최종 제출은 미션 2 이후 바꾼 점(노드 · 예외 처리 · 출력 키)을 반영해 최신 워크플로우 기준으로 다시 쓴다.
- 맨 위 기본 정보와 네 칸을 채운다.
  1. 다룰 업무와 문서 선정 이유: 누가 어떤 문서로 무엇을 판정하는지, 판정 기준
  2. 출력 키와 형식: 정답지 JSON의 키 이름 · 형식과 같아야 채점된다.
  3. 노드 구성과 이유
  4. 예외 케이스 처리 방식: 서류 누락 · 값 불일치 · 흐린 문서가 들어오면 어떤 값으로 넘기는지
- Use Case Explorer 카드에서 출발했다면 유즈케이스 번호(예: U001)와 카드에서 바꾼 점을 적는다. 노드를 빼거나 추가한 것도 변경 사항이므로 이유를 함께 적는다.
- 노드 표에는 하는 일 뒤에 **그 노드가 없을 때 생기는 문제나 그 설정을 고른 이유**를 한 줄 덧붙인다.
- 판정 기준은 수치와 조건으로 구체적으로 쓴다.
- 설계서의 기준값 · 결정값 표기 · 판정 노드가 실제 워크플로우와 같아야 한다.
- 예외 처리 표에 쓴 처리는 워크플로우에 실제 경로로 구현되어 있어야 한다.

### 4.2 워크플로우 JSON (가이드, 피드백)

- 최종 제출 JSON은 라이브러리에 게시한 설정(config) 버전과 같아야 한다. 내보내기 전에 워크플로우 이름 옆 설정 번호를 확인한다.
- 워크플로우별로 최신본 하나만 낸다.
- Extract 노드의 **항목마다 설명**을 Studio 추출 노드 설정의 설명 칸에 쓴다.
- 판단이 어려운 문서를 사람에게 넘기는 장치를 둔다. 판정 값에 '검토 필요' 같은 보류 값을 두거나, 별도의 사람 확인 칸을 둔다. 사람 확인 칸을 쓰면 정답지에도 같은 칸을 넣는다.
- 정답지의 키는 **모두 한 노드에서 함께 출력**하고, 그 노드의 키 이름이 정답지와 같아야 한다. 그 노드가 마지막 노드일 필요는 없다.
- 제출한 워크플로우는 동의를 받아 업스테이지 공식 라이브러리에 등재된다.

### 4.3 라이브러리 게시 (최종 제출만, 가이드)

1. 워크플로우에 **테스트 케이스 파일을 모두 올려 한 번 이상 실행**한다. 완료된 실행이 없으면 문서를 선택할 수 없다.
2. ⋯ → 라이브러리에 게시
3. 항목 작성
   - 이름: 워크플로우 이름 그대로
   - 설정 버전: 제출하는 workflow JSON과 같은 config 번호
   - 설명: 자동 생성
   - 썸네일: 선택
   - **샘플 문서: 테스트 케이스 파일이 전부 체크되어 있는지 확인한다.** 빠진 파일은 채점되지 않는다.
4. 승인 요청 → '승인 요청이 제출되었습니다' 창이 뜨면 신청 완료
5. ⋯ → 라이브러리 설정 → 게시된 워크플로우 링크의 링크 복사 → 구글폼에 제출

- 샘플 문서와 실행 결과가 함께 공개되므로 가상 · 공개 문서만 쓴다.
- 마감 전에 승인 요청과 링크 제출까지 마친다.

### 4.4 데이터셋 (가이드, 피드백)

- 최종 제출은 문서 20건 이상, 유형 ①~⑤가 모두 들어가야 한다.
- 실제 양식이나 템플릿을 찾아 가상의 값을 채워 만든다. 운영진은 값보다 **양식이 실무 수준인지**를 중점적으로 본다.
- 피드백이 든 보완 전 예시: 생성형 AI로 한꺼번에 만든 문서, 모든 문서 종류가 같은 디자인, 판정에 쓰는 값만 있는 문서
- 실제 양식을 찾을 수 있는 곳: 국가법령정보센터 별지 서식, 정부24 등 공공기관 서식 자료실, 대학 · 기관 서식 자료실, 회사 · 금융기관 공개 서식, 저작권을 확인한 검색 결과
- 외부 양식은 저작권과 이용 조건(공공누리 표시 등)을 확인하고 출처 표시 조건을 따른다.
- 실제 개인정보는 넣지 않는다. 가상 값임을 알 수 있게 표기한다. 예: `900101-1******`, `010-0000-0000`
- **문서, 설계서, 정답지에 평가와 관련된 문구를 넣지 않는다.**
- 정답지에 적은 케이스마다 해당 파일이 실제로 포함되어 있는지 확인한다.
- 파일 이름
  - 케이스 1건 = 파일 1개: `팀명_최종제출_set01.pdf` …
  - 통합 업로드로 여러 파일을 한 케이스로 묶을 때: 파일 이름 앞에 case_id를 붙인다. 예: `팀명_최종제출_A_신청서.pdf`
  - 어느 쪽이든 정답지의 `file` 값과 똑같이 맞춘다.

### 4.5 정답지 JSON (가이드, 피드백)

템플릿 구조(`task`, `unit`, `output_keys`, `decision_values`, `cases`)는 바꾸지 않는다.

```json
{
  "task": "업무 이름",
  "unit": "판정 단위 (예: 지원자 1명 = 케이스 1건 = 판정 1건)",
  "output_keys": ["키1", "키2"],
  "decision_values": ["판정값1", "판정값2", "검토 필요"],
  "cases": [
    {
      "case_id": "A",
      "file": "팀명_최종제출_set01.pdf",
      "documents": ["문서 종류1", "문서 종류2"],
      "answer": { "키1": "정답 값", "키2": "정답 값" }
    }
  ]
}
```

- `output_keys`: 정답 값을 내는 노드의 키 이름을 모두 적는다. 설계서 2번 칸과 같아야 한다.
- `decision_values`: 판정 키가 낼 수 있는 값을 모두 적고 '검토 필요' 같은 보류 값도 넣는다.
- `case_id`: 겹치지 않게 붙이고 유형표의 '판정 단위' 칸에도 같은 값을 쓴다.
- `file`: 데이터셋 파일 이름을 확장자까지 똑같이 적는다. 여러 파일이면 목록으로 적는다.
- `documents`: 그 파일에 든 문서 종류. 문서 건수는 이 목록으로 센다.
- `answer`: `output_keys`의 키를 하나도 빠짐없이 적는다.
- 키 이름은 대소문자 · 밑줄까지 출력 키와 똑같이 쓴다. (`student_id` ≠ `studentId`)
- 값 형식도 워크플로우 출력과 맞춘다. 판정 값은 `decision_values`에 적은 그대로 쓴다.
- 해당 값이 없는 목록 키는 `[]`로 둔다. 예: `"missing_documents": []`
- 판정 값은 설계서, 워크플로우 결정값, 정답지에서 글자까지 같게 쓴다.
- 정답이 '검토 필요'인 케이스를 반드시 포함한다.
- 정답을 문서와 한 번 더 대조한다.
- 저장 전에 JSON 검사기로 쉼표 · 따옴표 오류를 확인한다.

### 4.6 유형표 (가이드, 피드백)

- '유형표' 시트에 문서 1건을 1줄로 적는다. 한 파일에 여러 문서가 있으면 페이지별로 나눠 적는다.
- 회색 '예시' 줄은 지우고, '유형' 열 이름은 바꾸지 않는다.
- 칸: 파일 · 페이지 / 판정 단위(정답지 case_id) / 문서 종류 / 유형 / 시험 목적(한 줄) / 기대 결과(정답지 판정 값과 같게)
- 유형 이름은 아래 다섯 가지에서 고르고 **번호와 이름을 바꾸지 않는다.** 한 문서가 두 유형에 해당하면 둘 다 적는다.

| 유형 이름 | 뜻 |
|---|---|
| ① 단순 | 양식이 깔끔하고 값이 모두 맞는 기본 문서 |
| ② 양식 · 문맥 다양성 | 같은 업무인데 양식이나 표기가 실제로 다른 문서 |
| ③ 문서 결합 | 여러 문서가 한 파일에 섞여 들어오는 경우 |
| ④ 저품질 | 스캔, 촬영, 기울어짐, 흐림 등으로 읽기 어려운 문서 |
| ⑤ 예외 · 함정 | 서류 누락, 값 불일치, 경계값처럼 틀리기 쉬운 상황 |

- 운영진은 유형 칸을 참고해 문서를 직접 열어 본다. 유형은 문서의 실제 특성에 맞게 고른다.

### 4.7 데모 영상과 발표 자료 (최종 제출만, 가이드)

- 데모 영상: 최대 3분, 사용자가 서비스 화면에서 문서를 넣고 결과를 받기까지의 흐름이 보이게 찍는다. 가이드는 서비스 완성도보다 Studio 워크플로우 자체에 집중하길 권장한다.
- 발표 자료 흐름: 문제 정의 → 워크플로우 기획(사람이 하던 순서를 어떻게 옮겼는지) → 신뢰성 설계(틀릴 수 있는 상황을 어떻게 막는지) → 서비스 완성도(데모)
