# 정답지 자동 대조 스크립트 사용법

`scripts/verify-answers.ts`는 정답지(answer.json)에 적힌 케이스를 Upstage Studio 워크플로우로 **실제 실행**하고,
출력 키 값을 정답과 **글자 단위로** 비교하는 도구다.

운영진은 라이브러리에 게시된 워크플로우를 다시 실행해 정답지와 비교한다(실행 정확도 25점, 예외 처리 15점).
이 스크립트는 같은 일을 제출 전에 미리 해 보는 용도다. 관련 이슈: #7, #6, #14

## 1. 준비

### 1.1 패키지 설치
```bash
npm install
```

### 1.2 환경 변수
레포 루트의 `.env`(또는 `.env.local`)에 다음 값이 있어야 한다. `.env.example`을 참고한다.

| 변수 | 설명 |
|---|---|
| `UPSTAGE_API_KEY` | Upstage API 키 (`up_`로 시작). **절대 커밋하거나 채팅·이슈에 붙여 넣지 않는다.** |
| `UPSTAGE_AGENT_ID` | 실행할 워크플로우(에이전트) ID |
| `UPSTAGE_CONFIG_ID` | 실행할 config 번호. 최종 검증은 라이브러리에 게시할 config 번호로 한다. |
| `UPSTAGE_PROJECT_ID` | 에이전트가 속한 Project ID. 모든 요청에 `x-project-id` 헤더로 보낸다. |

키가 없으면 스크립트가 실행 전에 멈추고 안내한다. 키는 각자 터미널이나 `.env`에 직접 넣는다.

### 1.3 데이터 배치
정답지와 데이터셋 파일을 같은 폴더에 둔다. 정답지의 `file` 값이 폴더 안 파일 이름과 **확장자까지 똑같아야** 한다.

```
data/
  mission2/
    경크크_미션2_answer.json
    경크크_미션2_set01.pdf
    ...
  final/                       ← 최종 제출 데이터 (#6에서 작성)
    경크크_최종제출_answer.json
    경크크_최종제출_set01.pdf
    ...
```

## 2. 빠른 시작

```bash
# 1) API 없이 정답지·파일만 점검 (몇 초, 비용 없음)
npm run verify:answers -- --answer data/final/경크크_최종제출_answer.json --check-only --expect-prefix 경크크_최종제출_

# 2) 전체 케이스 실행 후 정답 대조
npm run verify:answers -- --answer data/final/경크크_최종제출_answer.json

# 3) 특정 케이스만 다시 실행
npm run verify:answers -- --answer data/final/경크크_최종제출_answer.json --cases D,E

# 4) 재현성 확인: 케이스마다 2번씩 실행해서 결과가 같은지 비교
npm run verify:answers -- --answer data/final/경크크_최종제출_answer.json --repeat 2
```

`npm run` 뒤의 `--`는 그 뒤 옵션을 스크립트에 넘기라는 뜻이다. 빼먹으면 옵션이 npm에 먹힌다.

## 3. 옵션

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--answer <path>` | (필수) | 정답지 JSON 경로 |
| `--dir <path>` | 정답지와 같은 폴더 | 데이터셋 파일이 있는 폴더 |
| `--check-only` | 꺼짐 | API를 호출하지 않고 사전 점검만 |
| `--cases A,B` | 전체 | 지정한 case_id만 실행 |
| `--concurrency <n>` | 3 | 동시에 실행할 건수. 1건에 약 5분이 걸리므로 늘리면 전체 시간이 줄어든다. 429가 자주 나면 줄인다. |
| `--repeat <n>` | 1 | 케이스마다 반복 실행 횟수. 2 이상이면 리포트에 재현성 표가 생긴다. |
| `--timeout <sec>` | 900 | 케이스 1건 최대 대기 시간. 넘으면 `timeout`으로 기록한다. |
| `--poll <sec>` | 3 | 상태 조회 간격 |
| `--config <id>` | `.env` 값 | 이번 실행에만 쓸 config 번호 |
| `--skip-keys <k1,k2>` | `reason` | 자동 비교에서 뺄 키. 서술형 값은 글자 일치를 기대하기 어려워 기본으로 뺀다. |
| `--expect-prefix <str>` | 없음 | 모든 `file` 이름이 이 접두어로 시작하는지 점검. 최종 제출 땐 `경크크_최종제출_` |
| `--out <path>` | `verify-reports/<시각>` | 리포트 저장 폴더 |
| `--keep-files` | 꺼짐 | 실행 후 Upstage에 올린 파일을 지우지 않음 (기본은 실행 후 삭제) |
| `-h`, `--help` | | 도움말 |

## 4. 스크립트가 하는 일

### 4.1 사전 점검 (API 호출 없음)
제출 가이드와 피드백의 정답지 규칙을 기준으로 확인한다.

| 점검 | 실패 시 |
|---|---|
| JSON 문법 | ❌ 오류 |
| 최상위 키가 템플릿(`task`, `unit`, `output_keys`, `decision_values`, `cases`)과 같은지 | ❌ 오류 |
| 케이스 키가 `case_id`, `file`, `documents`, `answer`인지 | ❌ 오류 |
| `case_id` 중복 | ❌ 오류 |
| `file` 이름의 파일이 실제로 있는지 | ❌ 오류 |
| `--expect-prefix` 접두어 | ❌ 오류 |
| `answer` 키 = `output_keys` (빠지거나 남는 키 없음) | ❌ 오류 |
| `decision` 값이 `decision_values` 안에 있는지 | ❌ 오류 |
| `file`이 목록(여러 파일)인 케이스 | ⚠️ 경고, 실행에서 제외 |
| 문서 수가 20건 미만 | ⚠️ 경고 |
| 정답이 `검토 필요`인 케이스가 없음 | ⚠️ 경고 |

오류가 하나라도 있으면 API를 실행하지 않고 종료 코드 2로 끝난다.

### 4.2 실행
케이스마다 `파일 업로드 → 워크플로우 실행 → 완료까지 상태 조회 → 결과 저장 → 업로드 파일 삭제` 순서로 진행한다.

- 429(요청 한도)나 5xx 응답은 2초, 4초, 8초 간격으로 최대 3번 다시 시도한다.
- 실행 요청은 응답을 최대 120초까지 기다린다. 서비스 기본값(30초)으로는 동시 실행 중 응답이 늦어 끊기는 일이 있었다. 우리 쪽에서 먼저 끊은 요청(`*_TIMEOUT`)은 서버에서 이미 job이 만들어졌을 수 있으므로 재시도하지 않고 `error`로 기록한다.
- 상태 조회가 일시적으로 실패해도 `--timeout`까지는 계속 조회한다.
- 서비스(`src/lib/upstage.ts`)와 같은 API 코드를 쓴다.

### 4.3 비교 규칙
워크플로우 마지막 단계의 출력 텍스트에서 `output_keys`의 값을 뽑아 정답과 비교한다.

- 출력이 `key: value` 텍스트이든 JSON 객체이든 읽는다.
- 인용 표시 `【†n】`는 제거한 뒤 비교하고, 제거했다는 사실을 비고에 남긴다.
- **문자열 값**: 앞뒤 공백만 정리하고 글자 그대로 비교한다.
- **목록 값**(정답이 배열인 키, 예: `missing_documents`): 출력이 JSON 배열(`[]`, `["역사 사료"]`)이어야 하고, 순서까지 같아야 통과다. JSON 배열이 아니면 실패로 표시한다.
- **키가 출력에 없으면** 실패로 표시한다.
- 출력 키 표기가 정답지와 다르면(예: `Scene_ID`) 값은 비교하되 비고에 표시한다. 가이드는 "대소문자 · 밑줄까지 똑같이" 쓰라고 하므로 이 표시가 있으면 고친다.
- `decision`은 텍스트 값으로 비교하고, `additional_values.enum` 값과 다르면 비고에 표시한다.
- 서비스 화면용 파서(`result-parser.ts`)는 값이 없을 때 "미지정 장면" 같은 기본값을 채운다. 이 스크립트는 **기본값을 채우지 않는다.** 출력에 없는 값을 있는 것처럼 통과시키지 않기 위해서다.

## 5. 결과 읽기

### 5.1 터미널
```
== 결과
  A#1  297s ✅
  B#1  281s ❌
      source_reference: 정답 세종실록 103권, 세종 26년 2월 20일 (1444년), 기사 ID: kda_12602020_001
                        출력 세종실록 103권, 기사명: …, 기사 ID: kda_12602020_001  (인용 표시【†n】 제거 후 비교)
  D#1  ...  ⛔ timeout

통과 1 / 2
리포트: verify-reports/20261110-120000/summary.md
```

### 5.2 리포트 폴더
| 파일 | 내용 |
|---|---|
| `summary.md` | 사전 점검, 요약 표, 재현성(반복 실행 시), 케이스별 키 비교 표(정답 / 실제 출력 / 비고) |
| `results.json` | 위 내용 전체를 JSON으로 |
| `raw/<case>-run<n>.json` | Upstage 원본 응답. 틀린 원인을 볼 때 사용 |

`verify-reports/`는 `.gitignore`에 들어 있어 커밋되지 않는다. 팀에 공유할 결과는 `summary.md` 내용을 이슈 댓글로 남긴다.

### 5.3 종료 코드
| 코드 | 의미 |
|---|---|
| 0 | 모든 점검과 비교 통과 |
| 1 | 불일치, 실패, 시간초과, 오류 중 하나 이상 |
| 2 | 사전 점검 오류 또는 잘못된 옵션 |

## 6. 틀렸을 때 어디를 고치나

| 증상 | 먼저 볼 곳 |
|---|---|
| 판정은 맞는데 `source_reference` 형식이 다름 | 출력 형식 확정(#1) → Instruct 프롬프트와 Extract 설명(#5), 정답지(#6)를 같은 형식으로 |
| `decision`이 다름 | 원본 응답(`raw/`)에서 판정 근거 확인 → 워크플로우가 틀렸는지(#5) 정답이 틀렸는지(#6) 문서와 대조 |
| `missing_documents`가 "JSON 배열 형식이 아님" | Instruct 프롬프트에 출력 형식을 명시(#5) |
| 출력에 키가 없음 | 정답 값을 내는 노드의 키 이름이 정답지와 같은지(#5) |
| `timeout`, `failed`, `error` | 해당 문서는 심사에서 0점 처리 대상. 원본 응답과 Studio 실행 기록 확인 |
| 반복 실행마다 값이 다름 | 프롬프트에 형식과 기준을 더 구체적으로 적어 출력이 흔들리지 않게(#5) |

## 7. 한계

- **실행 1건에 파일 1개만 된다.** Studio API가 job마다 파일 1개만 받는다(`docs/UPSTAGE_API.md`). 통합 업로드로 여러 파일을 한 케이스로 묶으면 이 스크립트로 실행할 수 없으므로, 케이스 1건 = PDF 1개를 권장한다.
- **API 사용량이 든다.** 2026-11-10 set01 1건 실행에 약 33,000 토큰이 들었다. 반복 실행(`--repeat`)은 그만큼 늘어난다.
- **운영진 채점과 완전히 같지는 않다.** 운영진은 라이브러리에 게시된 config로 실행한다. 최종 검증은 게시할 config 번호로 한다. 운영진 채점기가 `【†n】`이나 서술형 `reason`을 어떻게 처리하는지는 확인되지 않았다(#1).
- **reason은 자동 비교하지 않는다.** 리포트에 정답과 실제 출력을 나란히 보여 주므로 사람이 읽고 판단한다.
