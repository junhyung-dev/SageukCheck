# 해커톤 1차 온라인 심사 기준

이 문서는 세 부분으로 나뉜다.

- **1~4장 (공식 기준)**: 운영진이 공개한 평가 기준 슬라이드의 내용만 옮겼다. 슬라이드에 없는 숫자나 규칙은 넣지 않는다.
- **5장 (보충)**: 슬라이드에 없는 사항 중 다른 운영진 자료로 확인된 것과 아직 확인되지 않은 것.
- **6장 (팀 지침)**: 공식 기준을 지키기 위해 팀이 정한 작업 방식이다. 공식 기준이 아니다.

## 1. 개요

- 총점: 100점
- 최종 제출물을 평가 에이전트가 채점하고 운영진이 검수한다.
- 구성: 데이터 40점 + 워크플로우 60점

## 2. 평가 항목

"자동"은 원문에 자동 채점으로 표시된 항목이다.

### 데이터 (40점)

| 항목 | 보는 것 | 배점 |
|---|---|---:|
| 문서 선정 | 실제 양식처럼 다양하게 만들었는가 | 15 |
| 케이스 구성 | 직접 찾은 케이스까지 다섯 유형에 담았는가 | 15 |
| 정답지 품질 | 정답이 맞고 키·형식이 출력과 같은가 | 10 |

### 워크플로우 (60점)

| 항목 | 보는 것 | 배점 | 채점 |
|---|---|---:|---|
| 설계 논리 | 설계서에 왜 이렇게 짰는지, 카드는 바꾼 점 | 20 | |
| 실행 정확도 | 다시 돌린 결과가 정답지와 같은가 | 25 | 자동 |
| 예외 처리 | 추측 대신 '검토 필요'로 넘기는가 | 15 | 자동 |

## 3. 꼭 지킬 규칙 네 가지

| 구분 | 규칙 | 내용 |
|---|---|---|
| 0점 | 출력 키 | 정답지 키와 다르면 그 항목은 0점 |
| 0점 | 오류·시간초과 | 문서 한 건이 오류·시간초과면 그 문서 0점 |
| 감점 | 정답지 오류 | 틀린 정답이 많으면 정확도 감점 |
| 공개 | 결과 공개 | 채점 결과는 팀별·문서별로 공개 |

## 4. 참고 사항

- 키 이름의 띄어쓰기·대소문자는 무시한다.
- 서비스 데모는 2차 데모데이에서 본다.

## 5. 슬라이드에 없는 사항

슬라이드에 구체적인 설명이 없는 항목이다. 추측해서 채우지 않고, 운영진 자료로 확인한 것만 출처와 함께 적는다.
자세한 내용은 [`SUBMISSION.md`](SUBMISSION.md)에 있다.

### 다른 운영진 자료로 확인된 것

- **다섯 유형** (출처: 미션 2 보완 피드백 5장). 번호와 이름을 바꾸지 않고 쓴다.
  - ① 단순: 양식이 깔끔하고 값이 모두 맞는 기본 문서
  - ② 양식 · 문맥 다양성: 같은 업무인데 양식이나 표기가 실제로 다른 문서
  - ③ 문서 결합: 여러 문서가 한 파일에 섞여 들어오는 경우
  - ④ 저품질: 스캔, 촬영, 기울어짐, 흐림 등으로 읽기 어려운 문서
  - ⑤ 예외 · 함정: 서류 누락, 값 불일치, 경계값처럼 틀리기 쉬운 상황
- **카드** (출처: 산출물 제출 가이드 산출물 1, 피드백 1장): Use Case Explorer의 유즈케이스 카드다. 카드에서 출발했다면 유즈케이스 번호(예: U001)와 카드에서 바꾼 점, 바꾼 이유를 적는다. 노드를 빼거나 추가한 것도 변경 사항이다. 바꾸지 않아도 된다.
- **설계서 형식** (출처: 제출 가이드 산출물 1): 템플릿 docx를 채워 1장 분량 PDF로 저장한다. 회색 안내 · 예시 문구는 지운다. (분량은 Q&A에서 +1쪽까지 허용, 아래)
- **키 이름** (출처: 제출 가이드 산출물 5): 정답지 키는 대소문자 · 밑줄까지 출력 키와 똑같이 쓴다. 슬라이드 각주(띄어쓰기 · 대소문자 무시)와 표현이 다르므로, 두 기준을 모두 만족하도록 **글자 그대로 일치**시킨다.

### Q&A 공지로 확인된 것 (2026-11-09~10)

출처: Q&A 채널 공지 "최종 제출 전, 자주 헷갈리는 질문 정리", "헷갈리는 부분 질문 정리 2", "오피스아워 이후 질문 정리 1 · 2".

- **시간초과**: 운영진이 다시 실행할 때 케이스 1건(실행 1회)이 **15분** 안에 끝나지 않는 경우. 제출 전에 테스트 케이스 전체를 끝까지 한 번 실행해 확인한다.
- **채점 방식**: 운영진이 다시 실행한 결과를 정답지와 비교한다.
  - 키 이름은 대소문자 · 밑줄까지 정답지와 같아야 한다.
  - 판정 값처럼 값이 정해진 항목은 규칙으로 비교한다.
  - 근거 문장처럼 값이 정해지지 않은 항목은 LLM-as-a-judge가 문맥을 보고 판단한다. 판정이 같고 뜻이 같으면 표현이 달라도 된다.
  - 목록 키는 항목 내용까지 본다. 항목은 짧은 고정 라벨로 내고 설명은 reason 같은 별도 키에 둔다.
  - Instruct 결과의 `metadata.enum`과 content 둘 다 결과로 본다.
  - Studio 실행 결과 화면의 '정확도'는 평가에 반영하지 않는다.
- **판정 노드**: 워크플로우에 1개. 정답지 키는 모두 이 노드에서 함께 나와야 한다. 판단이 여러 노드에 나뉘면 마지막 Instruct 1개가 앞 결과를 참조로 모아 키를 한 번에 낸다. 긴 글을 만드는 노드는 그 뒤에 붙이고 정답지에 적지 않는다.
- **Other(미분류)**: Classify에서 Other로 빠진 문서의 결과는 채점하지 않는다. 정답지에는 케이스의 최종 판정만 적고, 무관한 문서가 섞였을 때의 처리(무시하고 판정 / 검토 필요)는 설계서 4칸 예외 처리에 적는다.
- **유형표 (결합 PDF)**: 문서 1건 = 1줄. 한 PDF에 문서가 여럿이면 줄마다 판정 단위 칸에 같은 case_id, 파일 · 페이지 칸에 같은 파일과 다른 페이지를 적고, **모든 줄의 유형 칸에 "③ 문서 결합"**을 적는다. 다른 유형도 해당하면 "① 단순, ③ 문서 결합"처럼 함께 적는다.
- **건수와 품질**: 20건 이상이면 되고 많다고 가점은 없다. 쉽다고 깎지는 않지만, 실제 기관 · 회사 서식에 값만 채운 문서, 다양한 양식, 저품질 등 실무 케이스 구성을 높게 평가한다.
- **외부 코드 범위**: 데이터 처리 · 수치 계산 · 조건 판단 · 규칙 검증은 Studio 노드(Extract · Validate · Instruct · Match)로 구성한다. 외부 코드는 Agents API로 워크플로우를 호출한 뒤 저장 · 화면 표시 · 알림을 하는 서비스 단계에서만 쓴다. 서비스 단계는 1차 평가 이후 "서비스 완성도"에서 평가한다.
- **설계서 분량**: 템플릿 기준 +1쪽까지. 되도록 1장으로 정리한다.
- **제출물**: 실행 결과 JSON은 내지 않는다. 운영진이 라이브러리의 워크플로우를 직접 실행한다. 최종 제출물은 가이드의 8종이다.
- **흔들림을 줄이는 방법(운영진 권장)**: ① 스키마 항목 설명에 형식 · 단위와 "읽을 수 없으면 null"을 적는다. ② Validate로 필수 값 존재 · 형식 · 서류 간 일치를 검사하고 실패하면 Instruct에서 '검토 필요'로 보낸다. ③ 판정 값은 결정값(enum)으로 고정한다.

### 아직 확인되지 않은 것

- [x] 시간초과로 판정되는 기준 시간 → 15분 (위 Q&A)
- [ ] "틀린 정답이 많으면"의 기준과 감점 폭
- [ ] `source_reference`처럼 값이 자유 형식인 문자열 키를 규칙 비교로 보는지, LLM-as-a-judge로 보는지

## 6. 팀 작업 지침 (공식 기준 아님)

공식 기준에서 바로 이어지는 작업만 적는다.

### 데이터
- 문서는 실제 사용되는 양식처럼 다양하게 구성한다. (문서 선정)
- 팀이 직접 찾은 케이스를 포함해 다섯 유형(5장)을 모두 채운다. (케이스 구성)
- 정답지는 원본 문서와 대조해 값이 맞는지 확인한다. (정답지 품질, 정답지 오류)
- 정답지의 키·형식이 워크플로우 실제 출력과 같은지 확인한다. (정답지 품질, 출력 키)

### 워크플로우
- 설계서에 단계별로 왜 이렇게 설계했는지 적는다. (설계 논리)
- 카드를 바꿀 때마다 무엇을 왜 바꿨는지 기록한다. (설계 논리)
- 같은 입력을 다시 실행해 정답지와 같은 결과가 나오는지 확인한다. (실행 정확도)
- 근거가 부족하거나 불확실한 결과는 추측하지 않고 '검토 필요'로 보낸다. (예외 처리)
- 문서마다 오류·시간초과 없이 끝나는지 확인한다. 실패하면 그 문서는 0점이다. (오류·시간초과)
- 결과가 팀별·문서별로 공개되므로 제출 전 전체 문서를 다시 실행해 문서별 결과를 확인한다. (결과 공개)

### 제출 전 체크리스트
- [ ] 문서가 실제 양식처럼 다양하게 구성되어 있다.
- [ ] 직접 찾은 케이스를 포함해 다섯 유형이 모두 채워져 있다.
- [ ] 정답지의 값이 원본 문서와 맞다.
- [ ] 정답지의 키·형식이 실제 출력과 같다.
- [ ] 설계서에 설계 이유와 카드별 변경점이 적혀 있다.
- [ ] 전체 문서를 다시 실행했고 결과가 정답지와 같다.
- [ ] 오류·시간초과가 난 문서가 없다.
- [ ] 불확실한 결과는 '검토 필요'로 처리된다.
- [ ] 5장의 아직 확인되지 않은 항목을 확인했다.
- [ ] [`SUBMISSION.md`](SUBMISSION.md)의 최종 제출 체크리스트를 모두 채웠다.
